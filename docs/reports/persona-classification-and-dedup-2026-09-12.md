# 페르소나 분류 비교와 로컬 중복 정리

2026-09-12. 대상: 127.0.0.1:55433/opod_persona_memory_local.

## 결론

상시 성격과 검색형 기억을 나누는 방향은 타 제품의 공개 설계와 일치한다. 그러나 항목 수가
많다고 분류가 좋은 것은 아니다. 현재 OPOD는 작성용 제목, 내용의 역할, 주입 정책을 구별할 수
있는 기반이 있지만, 동일 제목의 구버전과 보강본이 함께 활성 상태이고 성격·가치·감정·대인 반응의
책임이 겹쳤다. 분류의 우열이나 실제 대화 품질을 입증한 벤치마크는 없다.

## 현재 분류에서 구별해야 하는 축

- **작성 제목**: identity, personality, values, social_style, voice, boundaries, world 등.
  관리자가 내용을 찾기 위한 이름이며 현재 DB에서 의미 중복을 자동으로 막는 고정 분류는 아니다.
- **내용 역할**: identity / behavior / voice / lore / example / greeting / creator_note.
- **주입 정책**: always / retrieved / never_prompt 등의 실제 노출 정책.
- **대상 범위**: 캐릭터 공통 설정, 사용자와의 실제 관계·기억, 현재 대화 상황, 게시물 제작 규칙.
  한 인물의 사회적 성향과 특정 사용자와의 현재 친밀도를 같은 문장으로 확정하면 안 된다.

예를 들어 '칭찬에 쑥스러워한다'는 행동 성향이고, '지난번 사용자가 칭찬했다'는 사용자와의 사건이다.
'고향은 강릉'은 안정적인 배경이며 '지금 강릉에 있다'는 별도 근거가 필요한 현재 상황이다.
'짧고 수더분한 존댓말'은 말투지만 '해시태그 3~5개'는 게시물 제작 지침이다.

이는 비교에서 도출한 설계 판단이다. 이번 작업은 새 분류 강제·DDL·공통 프롬프트 변경 없이
현재 필드 안에서 내용과 활성 목록을 정리했다. 모든 축의 전용 관리 UI를 구현한 것은 아니다.

## 실제 로컬 변경

| 캐릭터 | 정리 전 활성 페르소나 | 정리 후 | 상시 블록 |
| --- | ---: | ---: | ---: |
| 한소이 | 19 | 11 | 6 |
| 서린 | 15 | 9 | 6 |
| 권도건 | 18 | 10 | 5 |
| 나희 | 17 | 10 | 5 |
| 합계 | 69 | 40 | 22 |

- 중복 역할의 구항목 19개와 보강본 내부 중복 항목 2개를 통합했다.
- 오래된 인사 4개와 예시 묶음 4개는 활성 목록에서 제외했다. 대화 예시 기능 자체를 없앤 것은 아니다.
- 총 29행을 soft delete했다. 삭제된 본문은 DB에 남아 있으며 변경 전 전체 dump와 스냅샷도 있다.
  현재 관리 API에는 복원 endpoint가 없으므로 되돌릴 때는 기록을 확인한 유지보수 작업이 필요하다.
- 보강된 정체성과 겹치던 옛 identity의 외형은 appearance로 분리했다. 세계관·관계·취향·제작 규칙의
  고유 내용은 남기고, 관계와 말투에 섞인 공통 경계 설명은 해당 담당 항목으로 모았다.
- 소이의 별도 initiative를 성격·대인 반응으로 합쳤고, 도건의 두 personality를 하나로 합쳤다.
- 소이의 캡션·공개 댓글 규칙, 서린의 셀프 촬영과 얼굴 비공개 방식, 나희의 제작 안전 규칙처럼
  DM 규칙과 다른 내용은 content_style에 보존했다. content_style은 never_prompt다.
- 작성 문서를 수정하거나 다른 항목으로 옮긴 데 맞춰 기억 25개의 source_refs를 다시 연결했다.
  실제 활성 원문, 같은 캐릭터, 인용문 바이트 범위와 해시를 모두 확인했다.
- **기억 125개의 본문·주입 정책·임베딩 값은 변경하지 않았다.** 사용자 기억·관계·요약과 관리자
  계정도 유지했다. 기억 내부의 추가 의미 중복 제거까지 했다는 뜻은 아니다.

## 검증과 한계

Existing owner: 관리 서비스 CharactersService와 CharacterRepository의 구조 저장·내용 검증·CAS·
출처 검증·soft delete·정렬을 재사용했다. 실제 HTTP 호출 대신 같은 서비스/저장소를 유지보수
트랜잭션에서 직접 호출했다. 새로운 제품 로직이나 인증 우회 endpoint는 만들지 않았다.

변경 전 58개 입력의 제품 ChatService.prepare 출력을 캡처했다. serializable 트랜잭션 안에서
정리를 리허설하고 같은 입력을 검증한 뒤 강제 rollback하여 전체 9개 테이블 스냅샷이 같음을
확인했다. 다시 한 트랜잭션으로 적용·검증·커밋하고 새 연결로 재검증했다.

확인 결과:
- 관리 서비스의 활성 목록, 분류 제목 중복 없음, 순서, 원문/조각 일치.
- 삭제 행의 원문 보존, 현재 기억 출처의 유효성, 캐릭터 간 혼입 없음.
- 58개 입력의 선택된 기억 ID와 순서가 정리 전과 동일.
- 이전 대화 원문 유지, 상시 프롬프트 해시 안정성, 요청 32,000바이트 이내.
- 사용자 기억 4개 테이블과 캐릭터 기본 행, 관리자 계정 변경 없음.
- 외부 채팅 LLM·임베딩 호출 0회. 실제 생성 답변이나 자연스러움은 미검증이며 not-reviewed 유지.

첫 실행에서 서로 다른 설치 경로의 pg Client를 Drizzle에 축약 인자로 넘겨 기본 포트 연결이
시도됐다. 해당 연결은 실패했고 변경 트랜잭션은 시작되지 않았다. 명시적 client 전달로 고친 뒤
원본 스냅샷 일치를 재확인하고 위 리허설과 적용을 통과했다. 다른 DB에 쓴 기록은 없다.

## 후속 — 성격·말투·공통 규칙의 역할 정리

사용자의 추가 `정리해` 요청으로 같은 로컬 DB의 현재40개 항목을 정리했다. 앞 절의 행 삭제를
다시 수행하지 않았다. 이번 변경은 제목/개수/주입 정책을 유지한 채17개 상시 블록의 내용 위치와
중복 표현만 수정했다.

- 25문장을 글자 그대로 다른 담당 항목으로 이동했다. 서린·도건·나희의 정체성에 섞인 자기 인식은
  성격/경계로, 소이의 비판 반응은 social_style로, 서린의 선택·갈등·반가움은 담당 위치로 옮겼다.
- 중복 표현16곳 중15곳은 이미 실제 요청에 포함되는 공통 정책을 재서술한 부분이다.
  나머지1곳은 도건의 social_style에서 voice와 중복된 해요체 설명이다. 부분 삭제 시 남겨야 하는
  특성은 별도 replacement로 보존했다. 말투·사생활·의료 및 동의 경계는 유지했다.
- source_refs가 변경 블록을 참조하는 기억1개의 출처만 새 원문 해시/범위로 갱신했다.
  기억125개의 본문·주입·임베딩과 사용자 기억, 관리자 계정은 변경하지 않았다.

중복 제거 문장의 원래 자리 제거, 모든 캡처에 공통 규칙이 계속 존재함, 기억 선택 ID/순서 불변,
출처 해시/인용 범위, 이전 대화·주입 정책·예산·캐릭터/사용자/계정 보존을 확인했다.
기존 `system-prompt.test.ts`와 `persona-router.test.ts`도 새로 실행해27개 테스트가 통과했다.
제품 코드가 바뀌지 않은 데이터 유지보수이므로 전체 build/E2E 재실행 대신 실제 DB 트랜잭션·
재연결·요청 캡처와 해당 공통 owner의 좁은 회귀 검증을 사용했다.

이것은 실제 생성 답변 테스트가 아니다. 외부 chat/embed0회, 사용자 품질 판정은 not-reviewed다.

모든 의미 중복을 자동 탐지하는 기능을 구현한 것도 아니다.
