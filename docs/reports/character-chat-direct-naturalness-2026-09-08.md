### 반복 표현과 모델 원인에 대한 확인

- 이번에 본 ‘셀렉’·‘오, 왔어요’는 새로 생성한 답변이 아니라 N1 원문이다. 최신 후보에서 같은
  문제가 재발했다는 증거로 합치지 않는다. 그렇다고 사용자의 문장·문맥 지적을 무효화하지 않는다.
- 당시 동결 요청의 도건 예시에 ‘오, 왔네요. 반가워요.’, 나희 예시에 ‘셀렉이 계속 안 끝났어요.’가
  들어 있음을 다시 확인했다. 두 캐릭터의 전후4문맥, 총16요청에서 확인한 입력/표현 겹침이다.
  입력과 출력의 겹침은 사실이나 그것만으로 모델의 내부 생성 원인을 확정하지 않는다.
- N1은 같은 `xiaomi/mimo-v2.5-pro`에서 전후 입력을 비교한 실험으로, 모델만 바꾼 비교가 아니다.
  따라서 모델 기본 한국어 능력·예시 영향·공통 지침 영향 중 어느 것이 주원인인지는 미확정이다.
  ‘모델 문제’ 혹은 ‘페르소나 단어 복사’는 인과가 입증된 결론으로 승격하지 않았다.
- D32의32본문에서는 ‘셀렉’·‘오, 왔’이 검색되지 않았지만 문맥이 인사/칭찬/커피로 제한된다.
  N1의 근황·알람·라면 문맥과 다른 표본이므로 기존 결함의 해결이나 재발률0을 뜻하지 않는다.
  원인 분리가 필요하면 동일 문맥·동일 입력에서 모델 한 변수만 바꾸는 별도 실험이 필요하며,
  이번 접수로 유료 실행을 승인받은 것은 아니다. 추가 모델 호출은 하지 않았다.

## D24 — N3: 마지막 발화를 배경 뒤에 두는 단일변수 후보

### 근거와 가설을 구분한다

사용자는 D23 이후 “다음 진행해”로 캐릭터 공통 직접 개선의 후속 작업을 요청했다.

남았다. 이는 새 지침이 문제를 해결했다는 증거가 아니며, 사용자가 배치를 원인으로 지목한 것도 아니다.

현재 조립은 `system → 이전 대화 → [실제 마지막 발화 + 배경 context]`다. 실제 HTTP 입력에서
알람 문맥의 마지막 발화는 UTF-8 41byte, 뒤따르는 시각·관계·사용 지침은 2,055byte였다.
네 합성 문맥 전체의 배경은 1,654~2,055byte다. 바이트 비율은 토큰 비율이나 모델 주의력의 측정이
아니다. **배경을 이어 쓰듯 반응하는 데 마지막 배치가 기여할 수 있다**는 가설의 신뢰도는
`unknown`으로 두며, 원인 규명이나 해결로 승격하지 않는다.

라벨만 바꾼 것이 아니라 **본문 구간을 실제로 나누고, 상시/조건부/제외 경로를 제품 코드에
연결했으며 캐릭터 기억의 회수 방식도 변경했다.** 같은 코드가 네 캐릭터에 적용된다.

변경한 것은 **DB 위의 구조화된 읽기 모델과 모델 입력 조립**이다. DB 테이블·원문을 직접
재작성하거나 이전 자료를 삭제한 것은 아니다. `.env`/제품 실행 설정도 바꾸지 않았다.
유료 모델 호출·외부 LLM 전송·신규 임베딩·개발 DB 접속·DDL·제품/검수 사이트 배포·commit/push는 없다.
정정·망각, 새 current scene 생성, 사용자 대화에 의한 공용 성격 자동 변경은 후순위로 유지했다.

### 레퍼런스를 어떻게 적용했나

- Character.AI가 설명하는 정체성·감정 논리와 authored/자동 기억의 구분은 **성격의 판단·반응은
  유지하면서 과거 자료의 쓰임을 분리**하는 근거다. 예시 자체를 모두 없애라는 근거는 아니다.
  [Definition](https://support.character.ai/hc/en-us/articles/50609183646875-5-Character-Definition),
  [Memory](https://blog.character.ai/memory/).
- Kindroid의 Backstory/Directive/Key Memories/Example Message와 Journal의 조건부 회수,
  SillyTavern의 Character/World Info 구분을 참고해 **제작 지침과 DM 말투를 분리하고,
  배경·사건은 관련 회수어가 있을 때만 읽는 경로**를 만들었다.
  [Kindroid Memory](https://kindroid.ai/v2/docs/memory/),
  [Kindroid Personality](https://kindroid.ai/v2/docs/customizing-personality/),
  [SillyTavern World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/).
- Nomi의 Identity Core/Mind Map, AI Dungeon의 Summary/Memory Bank, Letta V1의 memory blocks는
  소유권·개요·세부 기억을 구분할 참고 자료다. 그래프 DB, 자기 진화 Persona, 각 제품의
  비공개 알고리즘을 그대로 도입하지 않았다. 전체 원문 링크와 채택/비채택 이유는
  [연구 11.23](../character-chat-products-persona-memory-research-2026-09-03.md#1123-d28--공식-레퍼런스-재확인과-실제-personamemory-읽기-구조-변경)에 있다.

이번 재조사 근거는 공식 공개 문서다. SillyTavern 구현 원문 요청은 확보하지 못했으므로
런타임 내부를 확인했다고 주장하지 않는다. 외부 서비스의 기능 설명은 OPOD 자연스러움 개선의 증거가 아니다.

### 실제 분리된 구조

| 자료 | 기존 기본 입력 | 새 구조의 입력 조건 |
| --- | --- | --- |
| 성격·가치 판단·감정 반응·사용자 관계 경계 | 다른 자료와 한 덩어리 | 상시 유지 |
| DM 말투 | 캡션/해시태그 지침과 섞임 | DM 부분은 상시, 제작 부분은 제외 |
| 외형·주변 인물·직업의 상세 배경 | 상시 | 명시적 회수어가 맞는 턴만 |
| 독립 대화 예시·제작용 지침 | greeting 외 대부분 상시 | 이번 분류 후보에서는 DM 입력 제외, 원문 보존 |
| 캐릭터 기억79개 | 모두 상시 | 핵심 사실11개 상시, 나머지68개 조건부 |
| 사용자 장기 관찰/추론 | 상대 순위로 최대 top-K, 관련도0도 선택 가능 | raw cosine이 하한을 넘는 후보만 top-K에 선택 |

예를 들어 하나의 voice 원문에서 캡션/해시태그 구간과 댓글·DM 말투 구간을 실제로 나눴다.
relationships 안에서도 주변 인물의 배경과 사용자에게 허용되는 친밀함/경계는 다른 구간이다.
성격 차이를 없애지 않도록 후자는 상시에 남겼다. 성격·가치·감정 서술 내부의 짧은 인용 예문은
일부 그대로 남는다. **모든 직업 소재·인용문·어색한 어휘를 제거했다고 말하지 않는다.**

새 타입은 `kind`, `injection`, `recallKeys`이며, 기존 ID·내용·작성자 type/reason·시각은 보존한다.
기억의 fact는 preference/routine/goal까지 포함하는 비사건성 작성 사실의 큰 분류다.
예컨대 source `type=routine`을 삭제하거나 실제 수행한 현재 활동으로 바꾸지 않는다.

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 한소이 | 12 | 5 | 20 | 9 | 5 | 6 | 0 / 13 |
| 서린 | 9 | 4 | 16 | 7 | 4 | 5 | 3 / 13 |
| 권도건 | 12 | 3 | 17 | 9 | 5 | 3 | 5 / 20 |

15개 원문을40개 구간으로 분해하고 나머지30개는 본문을 유지했다. 원문45개는 전체 구간을
재결합하면 **byte-identical**이며 canon79개도 내용과 기존 메타데이터가 같다. 과거 사건은
26개이고 모두 조건부다. 한소이의 상시 canon0은 성격이 없다는 뜻이 아니다. 해당13개 canon이
모두 사건이며 정체성·성격·말투는 별도 상시 블록에 남아 있다.

회수어·상시 사실의 선택은 기존 source를 읽고 만든 **작성/분류 후보**다. 사용자가 승인한
새 성격 설정이나 사용자 품질 판정으로 취급하지 않는다. 캐릭터 이름/ID는 오프라인 자료에만
있고 제품 분기·정답 문장·캐릭터 전용 금칙어는 없다.

### 실제 경로와 안전장치

1. 원본 store → `RoutedPersonaStore`: 명시적 block ID/hash와 source 구간을 적용한다.
   구간은 UTF-8 문자를 자르지 않고 연속적이어야 하며 원문 전체를 보존해야 한다.
   분할 구간은 부모의 회수어를 무조건 물려받지 않는다.
2. canon은 모든 원본 ID에 정확히 한 개의 분류가 있어야 한다. 중복/누락/내용 hash 불일치는
   오류다. 분류된 사건을 `always`로 지정하는 것도 거부한다. 생성한 manifest는 비분할
   블록도 내용 hash를 고정한다. 원문 수정 후 예전 분류를 그대로 사용하지 않는다.
3. 현재 사용자 발화에 회수어가 일치하면 해당 캐릭터의 조건부 자료만 선택한다.
   대소문자/NFKC 정규화 후 부분문자열 비교이며 lore4개+canon4개 상한, 미일치면0개다.
   새 모델·임베딩을 호출하지 않는다. 조건부 canon은 사용자 학습 기억과 다른 섹션으로 들어간다.
4. 동적 선택은 turn context에만 들어가므로 캐릭터의 상시 system prefix는 턴마다 바뀌지 않는다.
   디버그에는 source ID/분류/주입 위치/이유만 표시하고 본문과 회수어를 넣지 않는다.
5. 사용자 기억은 기존 공통 ranking에서 **cosine > MEMORY_MIN_RELEVANCE**인 후보만 선택한다.
   기본0, 하한 이하 후보는 슬롯을 차지하거나 접근 시각을 갱신하지 않는다. 높은 중요도나
   최근성만으로 관련도0인 기억이 살아남던 동작을 회귀 검사로 재현한 뒤 수정했다.

구현 소유자: `src/persona/persona-source-projection.ts`, `routed-persona-store.ts`,
`persona-router.ts`, `character-recall.ts`; 연결은 `src/bootstrap/container.ts`와
`src/chat/chat-service.ts`/`turn-context.ts`; 사용자 기억 기준은 `src/memory/retrieval.ts`다.
기존 eval 구간 분리 코드는 제품 모듈을 재수출하므로 분리 알고리즘을 둘로 복제하지 않았다.

  이후 관련 회귀에서 실제 본문 제외·내용 버전 확인·조건부 회수·잘못된 상시 사건 거부를 확인했다.

  `canonCount`를 주입 개수로 오해한 테스트를 수정했다. 해당 필드는 기존대로 로드된 원본

### 아직 해결됐다고 말할 수 없는 것

- 명시적 회수어는 의역/대명사/긴 대화의 주제를 잘못 놓칠 수 있고 부분문자열은 과하게 맞을 수 있다.
  마지막 사용자 발화만 확인한다. 과거 메시지는 원래 history에 남지만 자동 문맥 해소는 추가하지 않았다.
  상한4는 항목 개수이며 token/byte 예산은 아니다. 긴 단일 source를 모두 짧게 재작성한 것도 아니다.
- cosine0 하한은 부호/0 점수 문제만 막는다. 실제로 무관한 문장도 양의 유사도를 가질 수 있다.
  실데이터의 positive/negative recall 검증 없이0.3 같은 더 높은 값을 최적값으로 정하지 않는다.
  내장 Stub/Postgres만 새 계약을 구현했고, 외부 store adapter는 옵션 지원을 별도로 확인해야 한다.
- core/summary 저장 구조, learned user-memory 생성 품질, 정정·망각, current scene은 그대로다.
  공용 성격을 자동 학습/재작성하지 않았다. 원문 성격이 부족한 일상 상황도 새로 창작하지 않았다.
- 분리와 회수·하한을 함께 구현했으므로 효과를 확인할 때는 Persona-only/canon-only/
  user-memory gate-only/결합 조건을 나눠야 한다. 형식 통과나 예전 사용자 선호로 성공을 추정하지 않는다.

### 적용/롤백 및 다음 검토

`PERSONA_ROUTING_MANIFEST_PATH`는 컨테이너 시작 시 읽는 선택적 설정이다. 이번 검증에서는
새 private manifest 경로를 실제 설정으로 읽어 raw store를 감싸는 경로까지 확인했다.
**운영 환경에서는 아직 설정하지 않았다.** 네 캐릭터만 담은 manifest를 전체 캐릭터 서비스에
곧바로 켜면 미분류 캐릭터가 실패하므로 대상 전체 분류/검토 없이 활성화하지 않는다.
원문 변경 시 분류 재생성과 재검토가 필요하고, 설정을 해제하면 Persona 주입은 legacy로 돌아간다.
사용자 기억 하한은 이 설정과 별개로 새 container 기본0이므로 배포 전 별도 영향을 검토한다.

다음은 새 구조를 근거로 조건을 나눈 실제 답변 검수다. 분류의 적절성, 회수어의 누락/과잉,
캐릭터별 판단·말투의 유지가 병합 전 핵심 검토점이다. 기존 N4는 독립 예시만 뺀 미실행
후보로 보존했고 새 결합 구조를 N4라고 바꿔 부르거나 기존 실행 계약을 재사용하지 않는다.
이번에는 원격 검수 페이지를 새로 게시하지 않았으며 예전 링크를 새 결과처럼 안내하지 않는다.

PAVE Knowledge Delta: `externally-evidenced` 공개 서비스의 구분과 `repo-evidenced` 공통 모듈/
소스 보존/회수 계약을 기존 연구 문서·ADR0008·인계에 반영했다. `user-confirmed` 수정 요청과
미검수 보존 원칙도 유지했다. 별도 코드 가이드가 없어 새 트리를 만들지 않고 ADR에 소유자와
실행 설정을 기록했다. 원인 신뢰도는 **관련도0 후보도 선택되는 코드 동작은 proven**,
**뜬금없는 실제 답변의 단일 원인·개선 효과는 unknown**이다. 새 troubleshooting 트리 대신
이 기존 직접 개선 보고서에 재현/수정/회귀/잔여 증거를 남겼다.
