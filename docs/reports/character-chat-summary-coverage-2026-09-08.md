# 캐릭터 챗 M2 — 대화 요약의 중복 계산 수정

2026-09-08 · 브랜치 `codex/character-chat-p1-persona-router`

> 후속 M3 수정과 최신 전체 검증은 [완료 경계 보고서](character-chat-completion-boundary-2026-09-08.md)에
> 기록했다. 아래 수치는 M2 당시 결과다. 후속 웹 coverage 미달은 캐릭터 목록 계약 검증을 보완해
> 해결했고 전체 검사도 다시 통과했다.

## 결과

**실제 메시지는 4개인데 6개를 요약했다고 기록하는 결함을 수정했다.**
대기 중인 작업끼리 같은 대화를 포함해도 이제 이미 처리한 부분을 다시 더하지 않는다.
구현·자동 검증은 통과했으며 공유 데이터 계약 변경이므로 병합 전 검토가 필요하다. 미배포 상태다.

| 순서 | 기존 | 수정 후 |
| --- | --- | --- |
| 첫 작업: 메시지 1~2 요약 | 2개 처리로 기록 | 2개 처리로 기록 |
| 대기 중이던 다음 작업: 메시지 1~4 포함 | 앞의 2개까지 다시 더해 **6개**로 기록 | 미처리 3~4만 반영해 **4개**로 기록 |
| 이후 새 대화 | 요약이 실제 대화보다 앞서 있다고 판단해 정상 갱신을 막을 수 있음 | 올바른 위치부터 요약 계속 |

## 원인과 변경

- 원인 신뢰도: `proven`. 실제 채팅 서비스로 두 작업을 만든 후 소비했을 때 6으로 기록되는
  실패를 확인했다. 역순 실행과 동시 요약 갱신에서도 같은 잘못된 결과를 재현했다.
- 기존 잠금과 재시도 중복 방지는 같은 job의 재실행/동시 쓰기를 막지만, **서로 다른 job에
  겹쳐 들어간 대화**까지 구분하지 못했다. 소비자는 입력 길이를 이전 처리 개수에 더하고 있었다.
- 새 작업은 대화의 시작 위치 `turnsStartOffset`을 가진다. 요약 처리 시 최신 처리 위치를 읽어
  아직 반영되지 않은 부분만 모델에 전달하고, 원본 범위의 끝까지 이동한다.
- 이미 전부 반영된 범위면 요약을 다시 호출하지 않는다. 앞부분이 누락됐으면 요약 단계가 실패한다.
  다른 작업이 먼저 갱신한 경우 최신 위치로 남은 부분을 다시 계산한다.
- 평가 도구에만 있던 “겹치는 앞 작업 생략”을 제거했다. 이제 평가도 모든 대기 작업을 공통
  요약 코드로 처리한다. 평가 실행 정보에 queue policy 버전을 남긴다.

캐릭터 이름·직업별 분기를 추가하지 않았다. 기존 JSON 작업 형식을 확장했으며 DDL은 없다.
backend의 다른 미커밋 작업, 개발 DB 데이터, 캐릭터 원문은 변경하지 않았다.

## 검증

| 검사 | 결과 |
| --- | --- |
| 겹친 작업의 순/역순 처리·재시도·다음 대화 | 통과 |
| 앞 구간 누락 후 재시도 | 누락 중 요약 미저장, 앞 구간 처리 후 정상 진행 |
| 동시에 다른 요약이 먼저 저장되는 경쟁 | 최신 위치 이후만 반영, 중복 계산 없음 |
| 실제 로컬 DB 큐 → 작업 소비 → 요약 저장 | 4개/revision 2, 완료 작업의 원문 payload 비우기 확인 |
| 제품 전체 테스트 | **344건 통과**, DB 통합 16건 포함 |
| 평가 도구 테스트 | **92건 통과** |
| 타입 검사·lint·build·dead-code | 통과 |
| 기존 coverage gate | 제품 92.39%, 평가 85.16%, 통과 |
| 정정·망각 유효성 구조 검사 | **POLICY-FAIL 유지** |

coverage는 DB 미연결 제품 328건/16 skip 및 기존 평가 집계 범위로 측정했다. 이후 DB를 연결한
제품 전체 344건을 별도로 통과했다. 웹은 이번 변경 대상이 아니며 이번 턴에 다시 검사하지 않았다.
유료 모델 호출·개발 DB 쓰기·DDL·배포·push는 0건이다.

재현 명령은 `npm test`, `npm run test:coverage`, `npm run test:eval:coverage`,
`npm run typecheck`, `npm run typecheck:eval`, `npm run lint`, `npm run build`,
`npm run dead-code`, `npm run eval:memory-structure`다. DB 통합은 `TEST_DATABASE_URL`을
localhost:5433의 로컬 DB에 지정했다. 작업 시작 전 큐 0행을 확인하고 고유 테스트 ID로 생성한 행만 정리했다.

## 해결하지 않은 것

- **기억 정정·망각 자체는 아직 아니다.** 이번 범위 자르기는 Summary에만 적용한다. observation
  추출과 성찰이 오래된 사실을 재저장하는 것을 막는 영속 장벽은 아직 없다.
- offset 없는 과거/수동 작업은 호환성을 위해 기존 동작을 유지한다. 이미 잘못 저장된 요약을
  자동 삭제하거나 복구하지 않았다. 실제 적용 시 구형 작업과 기존 요약 상태를 확인해야 한다.
- 숫자 위치는 원문 message ID가 아니다. 기록 수정·삭제에 대한 출처 추적이나 망각 근거로 쓰면 안 된다.
- 이전 batched 평가는 작업을 생략했으므로 새 실행과 호출 비용·결과가 다를 수 있다. 동일 조건의
  비교로 섞지 않으며, 이번 코드 검사만으로 자연스러움이나 최종 G1~G7 통과를 주장하지 않는다.

## 이어갈 작업과 기록

정정/망각에는 실제 원문 출처, 사용 가능한 기억 상태, 파생 요약의 의존 관계, 대기·실행 작업의
재저장 방지, backend history의 재노출 제어가 함께 필요하다. 스키마·history 소유자와 현재 미지원
경계는 [실행 계획 11.9절](../character-chat-products-persona-memory-research-2026-09-03.md)에 남겼다.

수정 위치는 `src/chat/consolidation-policy.ts`/`chat-service.ts`, `src/protocol/index.ts`,
`src/memory/consolidation.ts`, `evals/target.ts`와 관련 회귀 테스트다. 확인된 범위 계약은
[페르소나·메모리 적용 전략](../persona-memory-plan.md)에 `repo-evidenced` 지식으로 반영했고,
[다음 세션 인계](character-chat-next-session-handoff-2026-09-07.md)도 갱신했다.
이 저장소에는 코드베이스 가이드가 없고 소유자를 옮기지 않았으므로 새 가이드를 만들지 않았다.

병합 전 검토할 핵심은 **구형 작업 호환 경계**, **메시지 위치의 단위**, **평가의 작업 생략 제거**다.
