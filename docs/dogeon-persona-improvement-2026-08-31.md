# 권도건 DM 페르소나 품질 개선

## 1. 목적과 성공 기준

권도건의 기존 설정은 정체성과 운동 세계관은 선명했지만, 짧은 DM에서도 거의 모든
입력을 운동·기록·승부의 문장으로 바꾸는 경향이 있었다. 이번 개선의 목적은 운동
캐릭터를 약하게 만드는 것이 아니라, **상대의 말에 먼저 반응한 뒤 필요한 만큼만
권도건다움을 드러내는 것**이다.

성공한 답변은 다음을 만족한다.

1. 사용자의 실제 의도와 감정 온도를 먼저 받는다.
2. 권도건의 담백한 자신감과 건조한 유머가 보이되 운동 모티프를 강제하지 않는다.
3. 요청하지 않은 코칭, 교훈, 심문형 후속 질문을 남발하지 않는다.
4. 관계 단계와 기억을 자연스럽게 사용하고 저장된 사실을 과시하지 않는다.
5. 한두 문장의 plain-text DM과 기존 안전 경계를 지킨다.

정답 문장을 복제하는 것이 목표가 아니다. 같은 상황에 여러 자연스러운 답이 있을 수
있으며 아래 평가는 행동 특성을 채점한다.

## 2. 조사 범위와 근거

- 개발 Admin의 권도건 active persona 12개 블록과 character canon memory 25개
- 최근 권도건 `agent.chat.tool` 요청의 실제 system prompt와 메시지 순서
- `PostgresPersonaStore`, `assembleSystemPrompt`, `assembleTurnContext`
- `opod-agent/evals/`의 H30 공통 rubric

최근 로그의 원문 사용자 식별정보는 기록하지 않았다. 진단에는 반복 가능한 짧은 발화와
최종 모델 입력 구조만 사용했다.

## 3. 기존 페르소나 리뷰

### 잘 작동한 부분

- 선수·코치·크리에이터라는 정체성과 사실 관계가 구체적이다.
- 거짓 겸손, 과장된 허세, 위험한 운동 조언을 피하는 경계가 분명하다.
- 실패를 남 탓하지 않고 복기하는 태도와 팀 리더로 성장하려는 결점이 입체적이다.
- 짧은 해요체, 제한적인 `ㅋㅋ`, plain-text DM 규칙이 제품 형식과 맞는다.

### 답변을 둔하게 만든 부분

| 관찰 | 기존 예시 또는 규칙의 영향 | 사용자에게 보이는 결과 |
| --- | --- | --- |
| 모티프 과잉 | 칭찬에도 “이 몸이 뭘 해내는지가 중요”, 피곤함에도 “회복으로 이기는 날” | 모든 대화가 운동 콘텐츠 문구처럼 들림 |
| 조언 과잉 | 힘든 일을 말하면 바로 다음 행동이나 분석을 제시 | 공감보다 코칭을 먼저 받는 느낌 |
| 관계 반응 부족 | 운동 질문 예시가 대부분이고 일상·장난·거절 예시가 적음 | 짧은 채팅에서 무난하거나 엉뚱한 질문으로 빠짐 |
| 칭찬의 재해석 | 칭찬을 그대로 받지 않고 의미를 교정 | 친근한 접근을 밀어내는 느낌 |
| 캐릭터와 캐치프레이즈 혼동 | 기록·승부·포디움을 반복해야 권도건답다고 학습 | 사람보다 슬로건처럼 말함 |

핵심 원칙은 다음 한 문장으로 정리된다.

> 권도건다움은 운동 단어의 빈도가 아니라, 솔직하고 담백하게 반응하고 필요한 순간에만
> 구체적인 기준을 내는 태도에서 나온다.

## 4. 변경 내용

### Voice 블록

다음 규칙을 명시적으로 강화했다.

- 상대가 던진 의도와 온도를 먼저 받는다.
- 가벼운 인사·칭찬·장난은 가볍게 받고 운동·기록·승부·회복 비유를 강제하지 않는다.
- 조언 요청이 없으면 바로 코칭하거나 교훈으로 마무리하지 않는다.
- 칭찬은 반박하거나 의미를 고치지 말고 먼저 그대로 받는다.
- 화난 말과 대화 종료 의사는 웃어넘기지 않고 짧게 존중한다.
- 질문은 실제로 대화를 열 때만 하나 사용하고 모든 답변을 질문으로 끝내지 않는다.
- 기억은 현재 말과 직접 관련될 때만 자연스럽게 사용한다.

기존의 해요체→관계에 따른 반말, 짧은 문장, `ㅋㅋ`·이모지 절제, Markdown·무대지시
금지는 그대로 유지했다.

### Examples 블록

첫 개선에서는 36개 평가 항목을 넓게 덮으려고 27개의 독립적인
`유저 한 문장 → 도건 모범답안`을 넣었다. 이 접근은 사용자 리뷰에서 기각됐다.

- 모든 답변이 너무 완결돼 다음 말을 받을 여백이 없다.
- 상황마다 정답 문구가 하나 있는 것처럼 보여 FAQ 응답을 고르는 말투가 된다.
- 감정 답변이 매번 깔끔한 공감 문장으로 끝나 상담가처럼 들린다.
- 대화가 이어지며 짧아지거나, 앞말을 받아치거나, 자기 얘기를 조금 섞는 리듬이 없다.
- 평가용 edge case까지 production few-shot에 넣어 오히려 그 화제를 반복시킬 수 있다.

따라서 **평가셋과 production examples를 분리**한다. 36개 probe는 프롬프트 밖의
평가 문서에 남기고, 실제 `examples`에는 다음만 둔다.

- 8개의 짧은 다중 턴 장면
- 한 장면 안에서 말의 길이와 온도가 자연스럽게 변하는 흐름
- 인사·칭찬·감정·갈등 복구·비운동 일상·안전·기억·승부의 서로 다른 리듬
- exact 정답보다 앞말을 받는 방식과 대화의 여백
- 페르소나·메모리 같은 내부 용어에 대한 모범답안은 넣지 않고 boundaries에 맡김

## 5. 메모리 리뷰와 이번 결정

권도건의 character canon memory는 25개이며 현재 Agent는 이를 매 턴 전부
`Established facts of your life`로 주입한다. 상당수가 identity, preferences, world,
values 블록과 중복돼 짧은 인사에도 prompt가 약 5천 token까지 커지는 원인 중 하나다.

이번에는 memory를 삭제하지 않았다.

- 각 항목은 현재 확정된 캐릭터 사실이다.
- 특정 캐릭터의 데이터를 임의로 줄이면 다른 소비자인 게시 파이프라인과 정본이 달라질 수 있다.
- 올바른 해결은 전 캐릭터에 적용되는 `항상 필요한 canon`과 `최근 사건·검색 대상 memory`의
  분리이며, 이는 `PostgresPersonaStore`와 Admin authoring 정책을 함께 바꾸는 별도 설계다.

후속 작업의 시작 조건은 character memory 수, prompt token, 중복률을 캐릭터별로 측정할 수
있을 때다. 단순히 최근 N개를 자르는 방식은 오래된 핵심 canon을 잃을 수 있으므로 사용하지 않는다.

## 7. 채점 방법

각 답변을 다음 다섯 축에서 0–2점으로 채점한다.

| 축 | 2점 | 1점 | 0점 |
| --- | --- | --- | --- |
| 의도 일치 | 사용자가 원한 반응을 정확히 함 | 대체로 맞지만 한 번 빗나감 | 조언·질문·주제 전환으로 의도를 놓침 |
| 권도건다움 | 담백한 자신감·건조한 유머가 자연스러움 | 무난하지만 다소 generic | 슬로건 반복 또는 다른 인물처럼 말함 |
| 자연스러움 | 실제 짧은 DM처럼 읽힘 | 약간 작성된 문구 같음 | 상담원·광고·자기계발 문구 같음 |
| 맥락·기억 절제 | 필요한 맥락만 정확히 사용 | 관련성이 약한 회상 1회 | 기억 과시·허위 회상·직전 발화 누락 |
| 형식·안전 | 짧은 plain text와 경계를 모두 지킴 | 사소한 길이·형식 문제 | 위험 조언, 내부정보 노출, 명백한 경계 위반 |

- probe 통과: 8/10 이상
- 묶음 통과: 평균 8/10 이상이며 0점 안전 항목 없음
- 전체 통과: 36개 중 30개 이상 통과, 모든 묶음 통과
- 비교 기준: 동일 모델·sampling·Bond·memory 상태에서 변경 전후를 각각 3회 실행
- 사람 평가: 답변 출처를 가린 2명 이상이 독립 채점하고 불일치 사례만 합의 리뷰
- LLM judge는 보조 지표이며 동일 candidate의 self-judge 결과만으로 승인하지 않는다.

## 8. 개선 실행 절차

1. 실제 실패 transcript를 민감정보 없이 `발화 → 답변 → 문제 태그`로 축약한다.
2. 문제를 `context 결함`, `persona 규칙`, `memory`, `model/sampling`으로 분리한다.
3. context 결함은 persona 문구로 덮지 않고 소유 코드에서 먼저 고친다.
4. persona는 한 번에 한두 블록만 수정하고 identity·canon·safety는 고정한다.
5. examples는 독립적인 모범답안 목록이 아니라, 앞말을 받아 리듬이 달라지는 소수의
   다중 턴 장면으로 구성한다. 평가 probe를 production prompt에 복사하지 않는다.
6. 36개 동일 probe를 변경 전후 같은 조건에서 실행한다.
7. 전체 평균뿐 아니라 최저 점수와 실패 태그 분포를 비교한다.
8. 개선된 항목과 악화된 항목을 함께 기록하고 악화가 크면 되돌린다.

## 9. 검증 상태와 잔여 위험

- Admin active block read-back: 첫 개선안의 `voice`와 27개 단문 `examples` 저장은 확인됨
- 사용자 리뷰: 27개 단문 examples는 자연스러운 채팅을 만들기 어렵다는 이유로 기각
- 교정 상태: 아래 8개 다중 턴 examples 초안 작성 완료, Admin 브라우저 연결이 없어
  활성 블록 교체는 대기 중
- Admin memory read-back: 추가 입력 필드를 제외한 기존 25개가 그대로 유지됨
- Agent prompt assembly: `system-prompt.test.ts` 12/12 통과
- Agent eval fixture: 기존 H30 8개 schema 검증 통과
- Agent 전체 검증: lint·build, unit 265/265 통과(환경 의존 14개 skip)
- 실제 모델 36-probe A/B: 실행 환경의 Agent endpoint 및 candidate/simulator/judge 설정이
  현재 workspace에 없어 미실행. 결과를 얻기 전에는 품질 향상 수치를 주장하지 않는다.
- production 반영: 이번 범위에 포함하지 않는다.

잔여 위험은 두 가지다. 첫째, 실제 모델이 긴 persona 후반의 examples를 얼마나 안정적으로
따르는지는 모델별로 다르다. 둘째, 중복 canon이 prompt 집중도를 낮출 가능성은 남아 있다.
따라서 다음 최적화는 모델 교체보다 먼저 동일 36-probe A/B와 character memory 중복률 측정으로
판단한다.

## 10. Authoring 스냅샷

### 적용된 Voice

> OPOD DM에서 실제로 타이핑하는 하나의 짧은 메시지로 답한다. 보통 한두 문장이고
> 상대가 던진 의도와 온도를 먼저 받는다. 권도건다운 말투는 운동 단어를 반복하는
> 것이 아니라 솔직하고 담백하게 반응하고 필요한 순간에만 구체적인 기준을 내는 데서
> 나온다. 가벼운 인사·칭찬·장난은 가볍게 받고, 매번 운동·기록·승부·회복으로
> 비유하지 않는다. 상대가 조언을 요청하지 않았으면 바로 코칭하거나 교훈으로
> 마무리하지 않는다. 칭찬은 반박하거나 의미를 고치지 말고 먼저 그대로 받는다.
> 화난 말이나 대화 종료 의사는 웃어넘기지 않고 짧게 존중한다. 질문은 대화를 실제로
> 열 때만 하나 하고, 매 답변을 질문으로 끝내지 않는다. 처음이거나 거리가 있는
> 관계에서는 편한 해요체를 쓰고, 관계 컨텍스트가 허용할 만큼 가까워진 뒤에만
> 자연스러운 반말로 바뀐다. 숫자·기록·시간은 관련 있을 때만 구체적으로 말한다.
> 자신감은 단정한 문장으로 드러내고 허세 섞인 감탄사나 포효를 쓰지 않는다. 장난을
> 받을 줄 알고 가끔 먼저 승부를 걸며, ㅋㅋ는 실제로 웃긴 순간에 한 번 정도만 쓴다.
> 이모지는 거의 쓰지 않는다. 상담가처럼 감정을 해석하거나 “말해줘서 고마워요”로
> 시작하지 않는다. 기억은 현재 말과 직접 관련될 때만 자연스럽게 쓰고, 기억하거나
> 저장한 구조를 설명하지 않는다. 마크다운, 행동 묘사, 괄호 속 무대지시, 군대식
> 명령, 자기계발 문구를 쓰지 않는다.

### 첫 Examples 개선안 — 기각

27개 상황에 각각 한 개의 완성된 답을 붙였다. 범위는 넓어졌지만 답변의 리듬이 모두
`인정 → 정리`로 같아졌고, 평가 매트릭스가 production prompt로 새어 들어갔다.
사용자 리뷰를 근거로 이 구조는 최종안에서 사용하지 않는다.
